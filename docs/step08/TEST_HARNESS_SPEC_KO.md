# EVOLVE — STEP08 / 30% 평가 실행 설계 및 구현 인수인계
기준: `V575-STEP07-MONSTER-FEEDBACK-V614` · 본 문서는 **실제 플레이 검증 결과가 아닌 설계**임.

## 1. 검증 목적과 실행 가능한 기준
- 개발 로드맵의 공식 문구: "**STEP 08 타격감 첫 플레이 검증** — 잡몹/중간보스/TITAN 각각 근거리·원거리 시나리오에서 전투 템포를 비교."
- 완료 기준: 자동 측정으로 확인 가능한 오류/지표와 인간의 실제 체감 평가를 **각각 표시**, 문제별 확정/수정/보류 목록 제시. 시각 연출을 일단 더 추가하는 것이 목적이 아님.
- 후보 선정: 일반 적 crawler/runner/brute/spitter, 중간보스 alpha/sentinel/hunter/omega, TITAN은 현재 코드에서 확인된 BIO·VENOM 우선. 나머지 기획상 5종은 실제 스폰 가능한지 확인 후 가능한 항목만 시험. 가상 보스 데이터를 만들어 "통과" 처리 금지.
- 정상 장비 cannon/blades, 습득된 가시(shell)/채찍(tail)의 실제 이펙트만 사용. 기존 입/침 및 전격 상태는 임의 변경하지 않음.
- **신규 이미지 렌더링 불필요**. 재현용 기존 게임 화면 캡처(실행 증거)는 선택적으로 필요하지만 생성형 이미지 제작과 구분함.

## 2. 두 시험 트랙을 절대로 혼동하지 않기

### A. 재현 가능한 고정 단계 (functional)
1. 새 브라우저 context와 임시 저장소 사용; production 사용자의 개인 저장 데이터·관리자 설정 변경 금지.
2. 로컬 V614 복제 서버(`dist`), 페이지 `?evolveQA=1`를 사용할 것. 장비·맵·관리자 패널은 기존 테스트 helper를 활용.
3. **테스트가 이미 사용하고 있는** `requestAnimationFrame` 루프 정지 + `c.step(dt)` 수동 진행은 이 트랙에서만 가능. `c.draw()` 화면, 실제 hit 이벤트/데미지/HP/체력바/경고 노출, 중간보스 페이즈, 사망 에코 한 개를 검증한다.
4. 게임 시간 20~60s 재현과 의도한 적 수 1·10·50·180·250로 제어한다. 단, 실제 180~250개 적을 그리지 않은 경우 "250 synthetic hits"와 엄격히 분리; 메모리/프레임 성능 주장 금지.
5. `source_sha256`/`build`/장비/맵/오리엔테이션 및 도구 API 버전을 각 사례 JSON에 기록. 실패 시 screenshot/log과 재현 seed/조건 기록.
6. 3개 유형(ordinary/midboss/titan) 모두 근접과 원거리를 포함하여 원본 게임 코드의 수치나 피격 판정을 변조하지 않는다. 적 HP를 높여 촬영하는 QA fixture는 **플레이 밸런스 평가에 사용하지 않음**.

### B. 실제 경과 시간 재생 (realtime)
1. 별도 Chromium `context`를 열고 **requestAnimationFrame을 차단·재정의하지 않는다**. 게임 본래 루프를 가동한다.
2. `performance.now()`를 기준으로 실제 경과 60s/180s/300s를 측정하고, 10초마다 상태/장비/레벨/활성 적 수와 메모리(지원 시)를 샘플링한다. 브라우저 탭 visible 조건 필수; visibilitychange/일시정지/카드 선택 시간은 표시·제외하거나 별도 분류해 왜곡 방지.
3. 프레임 interval은 `requestAnimationFrame`과 callback time 차이로 샘플링. **이는 렌더 프레젠테이션 간격의 근사치**이며 진짜 GPU 프레임 수 또는 Galaxy S23+ 실기 FPS가 아니다. 가능하면 Long Animation Frames API(지원 여부 먼저 확인)와 Perf memory를 함께 사용.
4. 각 duration마다 `p50/p95/p99`, >50ms 비율, >100ms 비율, 최대 정지, 세션 지속/종료 사유, heap 시작/끝/최대(없으면 null), 샘플 수를 기록한다. 샘플이 너무 적거나 탭 hidden이면 `invalid`.
5. 화면 녹화가 실제 측정에 부담이 크면 촬영을 끄고 30초 구간 체크포인트에서 1장씩만 저장. 기록 도구 비용과 게임 렌더 부하를 혼동하지 않게 capture/no-capture를 구분.
6. 1분 결과를 먼저 검증한 뒤 3분, 다음 5분 세션을 **각각 별도 CI job/run**으로 실행하여 장기 작업 세션 만료를 최소화. 5분 측정은 가능할 때만 진행하고 미시행 시 미검증.
7. `headed=false` 데스크톱 CI 측정은 기기 간 절대 FPS를 결론으로 쓰지 않는다. 실기 Galaxy S23+ 플레이·발열·안드로이드 상태바 노출·백그라운드 복귀·실제 터치 중 3~5분 체감을 별도 보고로 분리.

## 3. 시각 품질과 타격감 평가 지표
- 한 번의 실제 명중: 공격 발생→HP 감소→피격 표정(움찔, 압축, 잔상) 시점을 대조. 임의 JS 이벤트로 만든 포즈를 실명중으로 착각하지 않는다.
- 총/칼/가시/채찍: 종류가 다른데 같은 포즈가 반복되는지, 기존 V612/V613 우선권이 유지되는지, 대형 대상이 너무 흔들리지 않는지 기록.
- 사망: 죽은 몬스터 1개당 기존 에코 **최대 1개**, 에코가 몬스터/플레이어/보스 경고를 덮거나 파티클 폭증하지 않는지.
- 중간보스: 다섯 등급과 네 프로필의 경고/근접·원거리 패턴, 피격 중 공격 예고가 사라지지 않는지.
- TITAN: BIO·VENOM은 해당 공격 패턴·페이즈 경고와 시야 간섭 평가; 이미지 스타일을 다시 만들지 않는다. 나머지 다섯 계획 보스 미구현 가능성은 `unavailable` 기록.
- 세로(393×852)/가로(852×393), reducedMotion 켬/끔, eco/normal, HP bar/canvas/GPU fallback을 최소 한 번 교차 비교.
- 사용자 체감은 1~5 점(충격·사망·가독성·리듬·피로도), **평가한 사람이 실제 있을 때만** 수집. 객관 로그로 재미 점수를 꾸미지 않는다.
- 중요도: P0 충돌·화면 소실·피해 수치 변경/세이브 유실 > P1 읽을 수 없는 경고/심각한 렉/명중 전달 실패 > P2 연출 균형 > P3 장식 개선.

## 4. 자동 검사 목표와 한계
- 기능 gate: 의도한 1대1 피해가 발생, 오버레이 없이 예고 보임, 죽음 에코 중복 0, 저장/메뉴 복귀 정상, 예전 무기/부위/보스·맵 회귀 검사 성공.
- 성능의 *권고 참고선*: p95 ≤33.3ms, >100ms 프레임 비율 <1%; 60fps급 목표를 뜻하지 않으며 절대 합격선으로 선포하지 않는다. 기기의 온도·환경·GPU·해상도 차이를 함께 적는다.
- 실제 몬스터 수는 카운터로 추적. 250개 hit event에 24개 포즈가 유지됐다는 STEP07 결과만으로 250개 움직이는 몬스터의 안정성을 주장하지 않는다.
- 브라우저 wall-clock 1/3/5min 실행을 하지 못하면 `not_executed` 또는 `blocked`로 보고하고 데이터 조작 금지.
- 모든 결과는 `scenario_id`, `baseline_hash`, `run_id`, `mode`, `elapsed_real_ms`, `game_elapsed_s`, `metrics`, `subjective`, `pass_state`, `evidence_paths`, `limitations` 구조로 작성.
- 모든 이슈에 재현 난도, 심각도, 영향을 받은 장비/맵, 수정안, 원복 범위, 실제 코드 변경 필요 여부 표시.

## 5. 2/3 (40~70%) 후속 실행 순서
- **40%**: 공용 재현/측정 scaffold `tests/combat_playtest_step08_browser.cjs`의 가장 작은 버전 구현. `docs/step08/PLAYTEST_MATRIX_V1.json`에서 cases 로드. 페이지·버전·스킬/보스 API 존재와 3종 클래스 검사. 단위 스모크/유효성 테스트. **게임 코드는 변경하지 않음**.
- **50%**: 일반/중간보스/TITAN 중 실제 사용 가능한 근거리·원거리 기능 매트릭스 실행(테스트별 5~10초 고정 게임 시간). 과다 효과/중복/경고와 죽음 기록, 화면 캡처 및 CI 원격 로그. 불가능한 타입 `unavailable` 명시.
- **60%**: 실시간 RAF 트랙 **60초 이상** 실시하고 지표 보고; 3·5분은 조건이 되면 단계별 진행(각 run 분리), 불가능하면 미검증. 브라우저 테스트가 게임의 가속 테스트를 성능 수치로 오인하지 않도록 확인.
- **70%**: 수집한 전체 이슈를 P0~P3/수정 vs 확인으로 분류한 후보 분석 보고서와 브라우저 증거 보존. 다음 3/3 구간에서 종합 보고 확정 전 `pass/partial/fail/untested` 명시.
- 각 10%마다 구현 코드 아닌 테스트/보고서 포함 **전체 Git repository recovery branch** 신규 생성. SHA/원격 파일 readback 확인; 이전 백업 삭제 금지.

## 6. 3/3 (80~100%) 완료 정의
- **80%**: 결과 항목별 실제 증거·검증 제한을 대조, 회귀 실패/P0/P1을 분리하고 우선순위별 수정 계획.
- **90%**: 플레이 검증 결과로 문제가 확인된 **최소 범위 수정만** 테스트→후보 CI→필요시 공개 배포; 단순 테스트 분석만으로 본게임 빌드 증가시키지 않는다. 수정이 필요하지 않다면 기존 V614 유지가 정상.
- **100%**: 실제 완료/미완료/사용자 체감 대기를 명시하고 최종 보고, 전체 저장소 원격 100% 체크포인트 재조회, 다음 STEP09 기획 예고. STEP09는 스킬 레벨 모델·카드 규칙 정리라 새 이미지 렌더링 **기본 불필요**(기존 카드 이미지를 바꿀 필요가 없다면).
