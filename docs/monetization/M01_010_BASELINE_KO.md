## 2. 기술/정책 위험: 바로 '돈 받는 버튼'만 붙여서는 안 되는 이유
- GitHub Pages는 정적 파일만 배포하며 서버측 결제 요청 검증 불가. 결제 완료/유료 보상 판정을 브라우저 JS, URL `?paid=true`, `localStorage.premium`만으로 처리하면 누구나 위조 가능하다.
- 따라서 **인증된 계정 연결 + 백엔드 영수증 검증 + 중복 처리 방지 장부 + 재구매 복원 + 환불/차지백 회수**가 유료 상품 출시보다 앞선 필수 의존성.
- 웹에서 직접 판매할 경우 외부 결제 제공자의 호스팅 체크아웃 + 서명된 웹훅을 받는 API 서버(서버리스 가능) + DB가 필요하다. **결제 성공 페이지로 돌아온 것만 보고 아이템을 지급하면 안 된다.**
- 향후 Google Play 배포 시 인앱 디지털 상품은 원칙적으로 Google Play Billing을 이용하고 구매 토큰을 백엔드에서 확인해야 함(제도상 적격 지역/계약의 예외는 별도). 스토어 결제 경로를 웹 결제 버튼으로 무조건 대체하지 않는다.
- 향후 Apple App Store 배포 시 인게임 화폐·기능·잠금 해제는 원칙적으로 IAP, 유료 재화 만료 금지, 복원 지원. 특정 스토어프런트/Entitlement 예외만 따로 준수.
- 웹 HTML5 게임 광고 Google H5 Ad Placement API는 신청/승인이 필요하며 승인된 AdSense도 필요. 모바일 AdMob은 별도 SDK/환경 요구. 승인을 받았다고 지레 광고와 보상을 활성화하지 않는다.
- 보상형 광고는 자발적 선택·보상 사전 고지·정상 플레이 방해 금지가 필요. 인앱 경제에 실질적 영향을 주는 보상은 서명 확인/재사용 차단 설계.

## 3. 수익화 전략에 관한 사업적 기준
1. **결제를 실제로 받아야 수익화 기능 완료**라고 판단. 유료 아이템 UI/테스트 숫자만 만든 것을 매출 구현 완료로 보고하지 않음.
2. 무료 플레이어도 주요 스테이지·스킬 진화·최종 보스를 접근 가능하게 유지. 결제를 통해 게임을 '망가뜨린 뒤 복구'하는 구조로 만들지 않음. 반복구매 동기와 체류 시간을 함께 설계.
3. 우선 상품 후보: 확정 금액 미정인 저가 스타터 패키지(1회), 외형/포인트 스킨(비소모), 성장 보조 재화팩(정해진 상한), 시즌형 연구 패스(기간 내 제공 가치가 확인되면), 선택형 보상 광고. 현재 상품은 전부 **기획 후보**.
4. **기존 DNA는 브라우저 localStorage 기반 재화**일 수 있으므로 현재 값을 그대로 '유료 구매한 DNA'로 인정하지 않는다. 새로운 유료 재화 `변이 결정`(가칭)의 원장/서버 검증을 별도로 마련한 다음 환전·상점 가격·무료 지급 조건을 통제.
5. 가챠/확률 유료 뽑기 도입을 선결조건으로 삼지 않음. 도입 시 별도 확률 공개, 규제, 연령 등 복잡성이 커짐. MVP는 **내용물 확정 상품** 위주.
6. 돈을 사용하지 않은 플레이어도 핵심 성장 루프를 맛볼 수 있도록 보상/장비/진화 드롭 빈도와 소모처를 설계한 뒤에 구체적인 가격·할인·광고 빈도를 정한다.
7. 실제 구매자의 유료 아이템이 저장 초기화, 다른 기기 로그인, 갱신, 뒤로 가기, 환불 등에서 유실·중복 지급되지 않는 것이 매출 UI보다 우선한다.

## 4. 유통 채널 정리
- **단기:** 기존 GitHub Pages 웹게임 유지 + 별도 HTTPS API/DB + 승인된 웹 결제 제공자 연결. 운영자가 외부 판매자/결제사업자 계약·인증 정보를 준비할 필요가 있다.
- **추후:** Android Play 패키징 또는 iOS 앱이 계획되면 *동일 상품/원장 데이터 모델* 위에 각 스토어 billing adapter를 별도 도입. 플랫폼별 금액·세금·환불 정책·규정 확인.
- 웹에서 결제 성공과 iOS/Android 유료 아이템 접근은 해당 스토어의 정책 범위에서 재검토; 크로스 플랫폼 자동 보장하지 않는다.
- 사용자에게 어떤 결제 서비스의 등록·비밀키 입력을 요구하는 시점은 **외부 계약이 필요한 때**라고 명시. 비밀키를 공개 repo나 Github Pages JS에 절대 기록하지 않음.
