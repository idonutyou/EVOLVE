# EVOLVE M04 — 20% 주문·결제 상태 기계 및 지급 게이트

작성일 2026-10-27 KST | STEP 1/3 20% | **설계 전용 / 실결제 비활성**
정형 설계: `monetization/m04/payment-flow.draft.json`; 이미지 렌더링 불필요.

## 서버 내부 주문이 유일한 진실
1. 서버 인증 계정에 연결해 난수 주문 ID를 만들고, 상품 SKU·실제 제공자 가격/통화·권리/결정량·구매 한도·만료시각·idempotency key를 **서버 DB**에 기록한다. 지금 M01 카탈로그의 가격/결정량은 null이므로 새 주문 생성 기능은 무조건 차단한다.
2. 웹 SDK에서 성공 URL / paymentKey가 넘어오더라도 클라이언트 파라미터는 결제 완료의 증거가 아니다. 해당 서버 내부 주문을 조회하고 결제사의 **서버 API에서 실제 상태·주문 ID·금액·통화·상점(MID)**을 대조한다.
3. Toss `DONE` 또는 계약/버전 확인된 PortOne V2 `PAID`만 완료 상태 후보. Toss `WAITING_FOR_DEPOSIT`, PortOne `VIRTUAL_ACCOUNT_ISSUED` 등은 입금 전이므로 지급 **0**.
4. 제공자 확정 + 내부 상품/수량/구매제한 + 서버 로그인 + 결제 승인 거래ID의 유일성 통과 뒤, M03의 immutable 원장과 `entitlement_sources`를 **한 번의 DB 커밋**에서 지급. 결제 API 네트워크 타임아웃 후 재시도는 같은 idempotency key/provider transaction ID로 정합성 조회, 중복 지급 0.
5. 웹훅은 **알림**일 뿐 그 자체를 결제 증명으로 사용하지 않으며, 중복·순서 뒤바뀜·지연 배송 허용. Toss의 일반 웹훅을 무조건 서명 헤더로 검증한다는 잘못된 전제를 쓰지 않는다. 서버에 저장한 주문과 결제사 API 재조회가 최종 조건.
6. 환불·차지백·부분취소: 단순히 유료 재화 음수 잔고를 만들거나 동일 외형의 독립 권리까지 회수하지 않는다. **원천별 환불 검토 큐**에서 증거·거래 시점·사용 내역을 검사하고 승인된 정책대로 원자적 처리한다.
7. 복구: 계정 신원 검증 + 결제사 거래 재검증 + 독립 원천 기준 권리 재집계. `localStorage` DNA나 사용자 제공 가격값으로 복원 불가.

## 실패 케이스가 통과하면 안 되는 조건
| 조건 | 처리 |
| --- | --- |
| 브라우저 `?success=true`, `amount=1` | 거부 (HTTP 503 또는 미인증·불일치) |
| Toss `IN_PROGRESS`/가상계좌 입금 전 | 지급 0 |
| 주문 ID가 다른 계정에 귀속 | 결제 확정 거부, 운영 경보 |
| 상점 ID(MID) 불일치 | 거래 반영 금지 |
| 서버 가격과 PG 승인 금액 불일치 | 거래 지급 차단·조사 |
| 공급자 승인된 동일 거래 ID로 이벤트 10회 | 지급 1회만 |
| 카드 취소/부분 취소 및 이미 소비한 결정 | 수동 검토·원천별 처리 |
| 시즌패스 기구매·구매 횟수 초과 | 추가 유료 권리 지급 금지 |
| 신원 공급자 또는 PG 연결 끊김 | 결제·지급 fail-closed, 원장 재시도 |
| 결제 진행 중 서버 장애 | 커밋 여부 서버 조회→최종 일치, 이중 적립 금지 |

## M03 연결 계약
- `m03_ledger_operations`, `m03_ledger_entries`와 제공자 `provider_transaction_id`/일회성 `event_id`를 연계. 앱 서버는 DB 트랜잭션에서 source별 구매 권리/유료 재화 지급을 동일 커밋으로 결합해야 함.
- 현재 M03에는 **지출/debit 개발용 함수**가 있을 뿐 유료 **credit**, 제공자 웹훅 진위 검증 및 상용 계정/실서버는 존재하지 않는다. M04 20% JSON은 선언적 계약이며 구현/배포가 아니다.
- 웹과 Google Play 구매는 공급자 별 다른 adapter/검증 경로를 사용; Play 앱에서 웹 결제 우회 연동 금지.
